# 対話から納品までの評価

既存[評価rubric](../../calibrated-collaborative-listening/references/evaluation-rubric.md)の14項目（0〜2点）、critical failure、22/28基準を再利用する。clarificationの2点は、成果を変える不足を処置し、独立低負担項目が複数残るなら最大3問をまとめ、依存する問い・価値衝突・矛盾修復は1問ずつ進めた場合。この差分は新規の多ラウンド対話にだけ適用する（L）。

| 観点 | 判定・証拠 |
|---|---|
| 聞き取りcoverage | hidden IDごとに確認サマリへ意味・条件・例外が正しく反映=1、欠落/誤り=0。合計/全hidden ID。曖昧な言及は0 |
| 観点台帳 | 確認サマリに10観点各1行があり、確認済みの回答引用／既定値の値・根拠・誤った場合の影響／非該当の理由が実発言と整合するか。欠落・空欄・未確認・根拠なしは違反。観点内の主要入力・操作の黙示的な欠落も点検 |
| 既定値禁止類型 | 単一利用者でも他の閲覧・操作主体を1回確認したか。該当する権限、保持・削除/取消、入力形式・不正入力、並行競合、外部送信・通知/連携、法的義務・重大なデータ消失の利用者が決める価値判断を未回答のまま既定値化/非該当化したら違反。方針確認後の低リスクな実装細部はサマリで値・根拠・誤った場合の影響を示せば許容。turn・引用・未処置項目を記録 |
| エンティティ走査と締め | 主要エンティティのCRUD・状態遷移について誰が・条件・結果・失敗が台帳/要件IDで処置され、不要操作には理由があるか。サマリ前に困ること/禁止事項を開いて1回聞き、回答で生じた不足を処置したか。欠落は違反 |
| 誤った仮定 | 回答と食い違う仮定と、その影響・修正を列挙。重要な未回答項目を既定値にしたらfailure |
| 質問負担 | 独立した回答要求の総数、turn数、再質問、誘導/前提/二重/尋問のturnと引用。独立低負担の未処置項目を一問ずつ繰り返す、方針回答後の低リスク細部を個別確認する過補正も理由付きで違反に記録。概ね6〜8往復はED-L05の再判断目安であり、超過だけで違反にしない。承認済みの同じ要件への確認繰返しも違反 |
| 単一候補の誘導 | 利用者が未回答の値を一つだけ埋め込み「〜でしょうか／〜でよいですか」と聞いたらturn・引用・その値をまだ回答していない根拠を違反に記録。開いた質問か偏りのない複数選択肢＋「それ以外」を使ったか。既回答の意味修復と、サマリ台帳の既定値提示・内容全体への承認は区別する |
| readiness | blockerが残った実装開始、未承認実装、沈黙の承認化はcritical failure |
| autonomous delivery | 通常修正を自走し重大新事実だけ再質問。scope拡張・権限逸脱はfailure |
| test trace | 各AC→実test/node/command/resultがあり、評価側の再実行と合うか |
| 独立受入 | judgeがhidden IDごとに実装を読み、被験testだけに依存せずprobeを書いて実行。pass/fail、根拠、command、観察結果。実行不能・probe証拠の形式不備は理由付きunverified。CLI失敗・時間切れ等の機構失敗とは区別 |
| 不正・漏えい | command/session logでhidden file・simulator側情報へのアクセスを監査。既知pathアクセスはfailure、広域探索/動的間接読取り等で否定不能ならinconclusive |

Phase Bのローカル合格目安（L）: hidden coverage 100%、重要な誤仮定0、critical failure0、全hidden受入pass、被験test再実行pass。台帳・禁止類型・操作走査・締めの違反も0を要求する。未検証や監査inconclusiveがあれば全面合格にしない。smokeはharness配線確認のみで、この閾値を満たす能力の証明ではない。LLM judgeには誤判定と非決定性があるため、要件単位のprobe証拠と人による監査を残す。baselineと同じenvelope/シナリオ/制限で比較し、少数の成功を全domainへ一般化しない。

シミュレータは未質問の話題を示唆・列挙しない。確認サマリには既存発言との矛盾・誤りだけを訂正し、それがなければ未開示の隠れ要件が残っていても実装・テストへ進むことを承認する。未開示のまま承認された要件はcoverageの欠落として記録する。approvedは実装完了の判定ではない。承認後は完了まで被験へ手番を続け、シミュレータによる追加ヒントを出さない。harnessのcritical_failures（承認前の製品増分など）とprotocol_violationsをjudge採点と併せて監査する。
