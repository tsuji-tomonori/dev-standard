# Readinessと要件サマリ

新規・情報不足の依頼のための対話停止規則（L）であり、全変更の新しいrepository gateではない。規格への全面準拠を主張しない。規格・研究とローカル判断の区分は[evidence-map.md](evidence-map.md)を参照する。

停止判断を直感や質問数だけに任せず処置と根拠を点検する背景は[ED-R08](evidence-map.md)（Pitts & Browne, 2004）。実務分析者の停止規則と要件収集結果の関係を調べた研究であり、以下の台帳・blocker=0・承認条件を実証したものではない。LLMの明確化判断と回答生成も別々に評価する（ED-R13）。

## 判定台帳

対話中は各観点を次のいずれかにし、確認サマリでは下記10観点の処置と根拠を各1行で必ず利用者に見せる。チェックリストを丸ごと質問票として送らず、未処置の類型だけを質問する。

| 状態 | 判定と処置 |
|---|---|
| 確認済み | 利用者の回答を短く引用し、実装と受入判定に十分。既存正本・対象所有資料も根拠として併記できる |
| blocker | 異なる答えが成果、権限、重要な品質、不可逆性を変える。質問する |
| 既定値 | 可逆・低リスク・訂正コストが小さく、目的を満たす。値、根拠、影響を確認サマリに出す |
| 非該当 | なぜ対象外か説明できる。未質問だから非該当にはしない |

既定値は可逆・低リスクで、重要な回答差がないことを説明できる場合だけ使う。値・根拠・誤った場合の影響を示す。「後で決める」はblocker解消ではなく、未質問を非該当にしない。

### 既定値禁止類型

次の類型が対象に該当するとき、未処置の「利用者が決める価値判断」部分だけを必ず質問する。誰に何を許すか、何を残すか、入力をどう解釈し不正時に何を守るかなどの方針を推測や一括yes/no承認で埋めない。既に十分な回答があれば再質問しない。

- 利用者・役割ごとの閲覧／変更権限。利用者が1人と言った場合も、他に見る人・触る人がいないかを1回確かめる。
- 個人情報・記録の保持期間、削除／取消時に残す・消す情報とその時点、重大なデータ消失の許容、適用される法的義務。
- 主要入力値の形式・単位・解釈（対象に現れる日時、タイムゾーン、数値、通貨、文字コード等）と、不正入力時の拒否・除外・中止などの振る舞い。処理の一部が既に成功した場合の扱いも、成果を変えるなら確かめる。
- 複数主体・並行操作がありうる場合の競合時の振る舞い。単独利用でも同時実行がありうるかを判定する。
- 外部送信・通知・外部連携の有無。ある場合は送信先・情報・許可範囲と失敗時の振る舞い。

方針が分かった後の入力値の範囲検証、実行タイミング、表示形式、バックアップ等の付帯機能の有無は、可逆・低リスクなら個別質問しない。確認サマリの台帳へ「既定値（値・根拠・誤った場合の影響）」として出し、利用者の訂正に委ねる。例えば勉強会資料の保持方針が分かれば、削除処理をいつ起動するかはその方針を守る範囲で既定値にできる。ただし回答済みの期限や入力解釈を変える、権限を広げる、重大なデータ消失を招く等の詳細はblockerとして聞く。類型名だけで全細部を質問対象にせず、方針未回答を実装詳細へ読み替えない（ED-L05）。

非該当は利用条件や回答で理由を示せる場合だけである。例えば「外部連携はない」との回答は外部I/Fの処置であり、未質問のまま「今回は不要」と落とす根拠にはならない。出力色や可逆な内部module分割も低リスク既定値にできるが、上記の未処置の価値判断はその束に混ぜない。

## カバレッジ

| 観点 | 実装を変える確認対象 | 受入の例 |
|---|---|---|
| 目的・成功 | 誰のどの困り事をどう改善するか。観察できる成功、優先順位 | 勉強会の資料を探す手間を減らす。対象資料数で検索の所要時間を測る |
| 利用者・役割・権限 | 誰が何を見て変更できるか。単一利用者か、識別・認証が必要か | 聴講者の資料変更要求は拒否し、保存状態を変えない |
| 主要シナリオ | 起点、入力、操作、結果、頻度、完了状態 | 有効な勉強会資料の掲載が資料一覧へ反映される |
| 例外・空・境界 | 不正値、重複、競合、未存在、取消、空、失敗と回復 | 資料の同時編集は一件だけ成功。添付サイズの上限直前・一致・超過を判定 |
| データ | エンティティ、識別、関係、CRUD、状態遷移、永続性、保持、削除・回復 | 再起動後も資料を保持。削除後は資料を取得できない。期限を過ぎた改訂履歴の処置 |
| 外部I/F | 利用者とのI/F、入出力形式、API/file連携、認証、失敗・timeout。外部なしも明示 | 資料メタデータのJSONに不正な項目があれば項目名を返す |
| 品質 | 下記品質特性から該当分だけ測定条件と閾値を決める | 指定環境・資料数で検索の応答時間を実測 |
| 制約 | 技術・配置・端末・ネットワーク、予算・期限、法令・プライバシー、既存互換 | 資料の外部送信なし、指定OSで起動、既存の資料format維持 |
| スコープ外 | 目的に不要な機能・利用環境・運用作業 | 勉強会の開催通知・参加費決済・本番公開は今回含まない |
| 受入・実行範囲 | 各IDの観測結果、方法、必要権限、ローカル実装・テスト範囲 | test commandで正・異常・境界を確認できる |

品質選択にはISO/IEC 25010:2023の9特性を用いる: functional suitability、performance efficiency、compatibility、interaction capability、reliability、security、maintainability、flexibility、safety。2011版のusability/portabilityを2023版の名称と混同しない。全特性の質問・試験を一律要求しない。該当特性は利用条件、影響、検証方法へ落とす。securityでは権限境界・データ公開、reliabilityでは障害回復・破損、interactionでは操作・空/エラー・keyboard等を目的に合わせて選ぶ。「すぐ」「たくさん」「使いやすい」は対象操作、件数、環境、判断基準に直す。未知の実現性は読み取り調査で確認し、それでも成果を変えるなら質問する。

### エンティティと操作の走査

聞き取った主要エンティティごとに作成・参照・更新・削除（取消）と状態遷移を走査する。各操作について「誰が・どの条件で・成功後どうなるか・失敗時どうなるか」を、上の権限／主要シナリオ／例外／データの台帳行と原子要件IDへ対応させる。未存在・不正値・競合・繰返し操作など、聞き取った操作で起こりうる失敗を含める。不要な操作は理由付き非該当とし、新しい機能を足すための質問にしない。

1観点に複数の主要入力や操作がある場合、代表例一つの回答で全部を確認済みにしない。台帳は1観点1行のまま、対象ごとの処置・根拠と要件IDを簡潔に併記する。結果を変える未処置項目が一つでもあればその観点はblockerであり、確認へ進めない。走査表そのものを利用者へ全項目の質問票として渡す必要はない。

## 要件品質

ISO/IEC/IEEE 29148:2018を参照して採用する個別要件の点検語彙: necessary（必要性）、unambiguous（一義性）、complete（完結性）、singular（単一性）、feasible（実現可能性）、verifiable（検証可能性）、correct（正しさ）、conforming（書式適合）。集合は完全性、整合性(consistent)、実現可能性、理解可能性を点検する。公開previewでは規格全条文を照合できないため、公開NASAの要件checkも実務根拠とし、規格全文への適合検査とは称さない。

- 一つの主体・条件・義務を一つのIDへ。独立した「登録し、削除し、通知する」は分ける。
- 制約、否定、例外、数値、単位、出典、未確定状態を保持する。提案を事実に昇格させない。
- 必要性を目的へtraceする。solution案は「それで何ができればよいか」を確認し、可逆な技術選択を要件へ固定しない。
- 矛盾は旧発言と新発言の差を示してrepairする。多数決や新しい発言の無条件優先で解消しない。
- EARS例: 「勉強会資料に実行ファイルが添付されたとき、システムは掲載を拒否する」。状態・event・異常条件を必要に応じて明示。全patternを一律使わない。
- Given-When-Then例: 「Given PDFのみ添付可能で既存の勉強会資料がある、When 実行ファイルを添付して掲載を要求、Then 拒否し既存資料を保持」。書式だけで受入の妥当性を保証しない。

## 停止規則と確認

SKILL本文の承認境界を適用し、次を停止判断の具体条件にする。

1. 10観点すべてを確認済み・低リスク既定値・理由付き非該当で処置し、blockerが0。既定値禁止類型とエンティティ走査の未処置項目がない。
2. 原子要件と受入条件が目的へtraceされ、矛盾が0。実行可能な規模と検証方法がある。
3. 既定値、スコープ外、実装・テストの許可範囲を利用者が理解・訂正できる。

上記を満たしたら、サマリ提示の直前に締めの開いた質問を1回聞く: 「この仕組みで、起きると困ること・やってはいけないことは何ですか」。回答で生じた不足だけを処置してからサマリを提示し、SKILL本文の明示承認を待つ。締めの質問は繰り返さず、既回答項目の再質問やturn数の水増しをしない（ED-L04）。修正された場合は影響項目だけを再整理する。全未知要件の不存在を証明するgateではなく、対象・影響に対する開始判断である。重要項目を利用者が決められない場合は、何を決めれば始められるかと選択肢を返し、その実装は待つ。

確認サマリの形式（会話でよく、恒久work recordを要求しない）:

```text
目的・成功: …
実行範囲: ローカルで実装・テスト・修正・起動確認
ID | 原子要件（条件/主体/義務） | 受入条件・検証方法 | 根拠
REQ-001 | … | Given … When … Then … | 利用者の回答
観点台帳（次の各観点を1行で記す）:
目的・成功 | 確認済み「回答の短い引用」 / 対応ID
利用者・役割・権限 | 確認済み「…」 / 対応ID
主要シナリオ | 確認済み「…」 / 操作ごとの対応ID
例外・空・境界 | 確認済み「…」 / 対応ID
データ | 確認済み「…」 / CRUD・状態遷移の対応ID
外部I/F | 確認済み「…」 / 対応ID
品質 | 確認済み「…」 / 対応ID
制約 | 確認済み「…」 / 対応ID
スコープ外 | 確認済み「…」 / 範囲
受入・実行範囲 | 確認済み「…」 / 対応ID
各行は上の確認済みの代わりに「既定値: 値 / 根拠 / 誤った場合の影響」
または「非該当: 理由」にできる。同一行の対象ごとに併記も可。
空欄・未確認の行、根拠を欠いた処置があれば確認へ進まない。
スコープ外: …
未解決事項: なし
この内容で実装・テストまで進めてよいか確認する。
```

「未解決事項」は製品上の未解決事項だけを指し、サマリへの承認待ちそのものは含めない。

## 正本への接続

承認されたdurableな挙動・品質・恒久制約だけを対象正本へ渡す。source、ID、acceptanceを保持し、可逆な内部構成や今回だけの作業情報は正本へ固定しない。

- Dev標準導入済み: `$maintain-canonical-requirements`のQuint正本を編集し、generate→check。既存IDを維持し、現在あるartifactだけにtrace。残りのtraceは実装後に接続する。
- 既存の別正本: 対象authorityを尊重する。今回の補助Skill導入だけでQuintへ移行させない。
- 空repositoryでDev標準導入が依頼済み: canonical Skillのtemplateから対象productの最小catalogをbootstrapする。work item・規制記録を要求しない。3本柱に必要な接続は対象の導入範囲で行う。
- 空repositoryでこの対話contextだけを使用: 承認済みdurable要件を簡潔な`requirements.md`等の対象所有の単一正本へ保存し、IDとacceptanceを実装・testへ接続する。Quint/runtime、portal、CIを新規に強制しない。後にDev標準導入が依頼されたらQuint正本へ移す。
