# 曖昧な一言から実装・検証まで

最初の依頼は日常の言葉で十分です。たとえば「学習塾の欠席連絡を簡単にしたい」「社内勉強会の資料を探しやすくしたい」「園芸日誌を続けやすくしたい」。目的や困った場面が一つあると、agentは成果を変える不足から聞けます。技術用語や全要件の一覧を用意する必要はありません。

## agentへ渡すcontext

`elicit-to-delivery`は新規app/systemの情報不足に使う補助Skillです。通常の変更が十分定まっていれば、新しい聞き取りや確認を追加しません。[導入ガイド](getting-started.md)のinstallerで選択できます。

```bash
python tools/install_reference.py --target /path/to/target --profile elicit-to-delivery --host codex --apply
```

このprofileは新Skillと既存の傾聴Skillを配布します。既定portable setは入口と3本柱の4 Skillのままです。Dev標準全体を導入する場合は既存のdefault/full profileを選びます。導入先のbranch、merge、CI、commit形式は維持します。

agentへの開始指示例:

```text
$elicit-to-delivery を使って進めてください。
社内勉強会の資料を探しやすくしたいです。今はメールに散らばっていて、必要な資料が見つからず困ります。
成果を変える不足だけを少しずつ聞き、十分そろうまで実装を待ってください。
10観点の根拠付き台帳・原子要件ID・受入条件・スコープ外・未解決事項をまとめて確認後、
ローカル実装・テスト・失敗修正・起動確認まで自走し、実結果を報告してください。
外部サービスへの書込み・本番公開・mergeは含みません。
```

既に分かる利用者、期限、端末、外部送信の制約、既存repositoryの場所は付けてください。secret・実顧客情報は渡さず、合成例や項目定義を使います。Skillのないhostへcontextを渡す場合は、[SKILL.md](../../.agents/skills/elicit-to-delivery/SKILL.md)、そのreferences、依存する傾聴Skillを読める形で渡します。入口文だけを貼ってreferencesを欠落させないでください。

## 期待する対話

agentはまず目的と最近の例を聞き、回答に沿って利用者/権限、操作と例外、データと保持、I/F、必要品質、制約、対象外、受入を整理します。未処置の独立低負担項目が複数あれば最大3問をまとめ、依存する問い・価値衝突・矛盾修復は1問ずつ進めます。小規模アプリは概ね6〜8往復以内でサマリへ到達する目安を使い、超えそうなら一括化・既定値化を再判断します。上限や研究上の最適回数ではありません。全チェックリストへの回答や、毎turnの全復唱は要求しません。

「すぐ」「たくさん」のような表現が受入結果を変える場合は具体基準を聞きます。権限・保持・入力解釈・競合・外部作用等では利用者が決める価値判断を聞き、方針回答後の低リスクで可逆な実装細部は個別確認せず、確認サマリの既定値台帳へ値・根拠・誤った場合の影響を示します。未回答の値を一つ埋め込んだ確認は避け、開いた質問か偏りのない複数選択肢と「それ以外」を使います。利用者が要件サマリを明示承認するまで、製品ファイル・テスト・scaffoldの作成・変更を待ちます。調査・整理は進められます。

未処置の重要事項がなくなったら、agentは起きると困ること・禁止事項を開いた質問で1回聞き、その回答を処置してから以下を一度まとめます。

| 項目 | 利用者が確かめること |
|---|---|
| 目的・成功 | 困り事と成功基準が意図どおりか |
| 原子ID・受入条件 | 誰が何をどの条件でできるか。例外・権限・保持が抜けていないか |
| 10観点の台帳 | 各行の確認済みの回答引用、既定値の値・根拠・誤った場合の影響、非該当の理由が合っているか |
| 既定値と根拠 | 仮定を受け入れられるか、訂正する箇所はあるか |
| 非該当・スコープ外 | 今回不要な範囲が一致するか |
| 未解決事項 | 空か。重要な「後で決める」が隠れていないか |
| 実行範囲 | 実装・テストと外部操作の権限が意図どおりか |

「この内容で進めてください」または訂正を返します。沈黙は承認になりません。承認後は通常の実装・修正の再許可を取らず進め、新事実が成果・重要制約・価値選択・権限を変える場合だけ相談します。

空repositoryでこのcontextだけを使う場合は、承認済み要件を対象所有の小さな単一正本へ残します。Dev標準導入が依頼済みならQuint正本へbootstrapし、3本柱へ接続します。大きな管理仕組みの導入を聞き取りの前提にしません。

## 完了報告の読み方

最初に実装したものと起動方法を確認します。次に要件ID↔testの対応表で各受入条件の実行commandと実結果を見ます。正常系だけでなく該当する異常・境界・権限・永続性が検証されたかを確認します。仮定は実装結果との意図の差、未達・未検証・残存リスクは達成主張の限界を示します。Dev標準使用時は正本generate/checkと実装由来設計のpath・drift検査結果も含みます。

Skillが置かれたことやtest成功だけで、すべてのアプリやモデルの完全性が保証されるわけではありません。根拠は[専用evidence map](../../.agents/skills/elicit-to-delivery/references/evidence-map.md)、gpt-6-luna単体の評価方法は[評価harness](../../evals/elicit_to_delivery/README.md)を参照してください。Phase A2のfake CLI検査は配線確認、能力の本評価はPhase Bで監査役がsandbox外から行います。
